# Worklog Studio 최종 계획

## 이 작업의 최종 목표

현재의 일자별 대량 프롬프트 메모를 다음 조건을 만족하는 **여러 운영체제·여러 Agent 공용 업무 처리 및 영구 기억 시스템**으로 개편한다.

1. 사용자는 Domain과 Milestone의 주요 목표, 사전 지식과 참고자료를 관리한다.
2. 사용자 또는 Agent는 목표에 연결된 Task를 만들고 프롬프트 초안과 실행용 Meta Prompt를 별도로 관리한다.
3. Agent는 승인된 최신 Meta Prompt, 관련 Knowledge와 Reference를 사용해 Task를 일관되게 수행한다.
4. Task 수행에서 확인된 사실, 결정, 제약, 쟁점, 실패와 인수인계 내용을 고유 ID의 Knowledge graph로 영구 보존한다.
5. macOS, Windows와 Linux 사용자는 Flutter 데스크톱 앱에서 Task 생성·편집·시작·일시중지·재개·중단·완료와 자동 처리 정책을 관리한다.
6. GUI가 없는 Hermes·서버·CI 환경은 동일한 Worklog Core와 CLI를 사용한다.
7. GitHub Private 저장소를 유일한 정본으로 사용하고 각 환경의 SQLite는 설치·설정 없이 자동 생성되는 파생 인덱스로만 사용한다.
8. `under-claw-meta-prompt`, `under-claw-jarvis-plan-loop`, `under-claw-jarvis-plan`을 공급자 중립 실행 파이프라인의 기본 스킬로 사용한다.
9. macOS·Windows·Linux 설치파일 또는 headless bootstrap 하나로 쉽게 설치·업데이트·제거한다.
10. 최초 설치에서 target Git repository와 repository password를 설정하고 이후 각 환경이 같은 저장소 인증 정책으로 접속한다.
11. 실제 password, verifier, token, 고객정보와 환경 credential을 Git·설치파일·로그에 기록하지 않는다.

## 최종 시스템 형태

```text
                         GitHub Private Repository
                     YAML·Markdown 정본 / Event / Claim
                                    │
                ┌───────────────────┼───────────────────┐
                │                   │                   │
        macOS Flutter App   Windows Flutter App   Linux Flutter App
                │                   │                   │
                └───────────────────┼───────────────────┘
                                    │
                             Worklog Core
                    validation · sync · index · claim
                                    │
                 ┌──────────────────┼──────────────────┐
                 │                  │                  │
           local SQLite       OS secure store    Agent adapters
                                                      │
                                 Codex · Claude · Gemini · Hermes
```

각 환경의 GUI와 CLI는 같은 Core 계약을 사용한다. Agent나 모델별 구현 차이는 `RunnerAdapter`가 흡수하며, Task와 정본 데이터에는 특정 모델 ID를 고정하지 않는다.

## 표준 Task 처리 파이프라인

```text
Domain / Milestone Objective
→ Task Draft
→ under-claw-meta-prompt
→ Meta Prompt 검토·승인
→ under-claw-jarvis-plan-loop
→ 회차별 under-claw-jarvis-plan
→ 분리된 독립 검수
→ TARGET 9.5 이상이면 완료
→ Knowledge / Event / 후속 Task 기록
```

`under-claw-meta-prompt`는 프롬프트 변환만 담당한다. 실제 Task 실행 전체는 `under-claw-jarvis-plan-loop`가 감싸고, 각 loop 회차의 이해·계획·구현·검수는 `under-claw-jarvis-plan`이 수행한다.

## 구현 불변조건

1. Git의 YAML·Markdown만 영구 정본이다.
2. SQLite와 agentmemory는 삭제 후 복구할 수 있는 파생 데이터다.
3. GUI와 CLI는 같은 Worklog Core를 사용한다.
4. Task는 승인된 최신 Meta Prompt만 실행한다.
5. 실제 상태 전이는 immutable Event와 원격 compare-and-create 결과로 증명한다.
6. 같은 Task를 두 Agent가 동시에 실행하지 못하게 claim과 operation ID를 사용한다.
7. 자동 생성 Task는 기여할 Objective와 근거 Knowledge·Reference를 기록한다.
8. 특정 Agent·모델·운영체제를 데이터 모델에 고정하지 않는다.
9. 사용자는 Git, SQLite, Go, Flutter, Node 또는 Python을 별도로 설치하지 않는다.
10. 인증 provider는 표준 프로토콜과 보안 acceptance를 통과하기 전 확정하지 않는다.
11. 자체 암호 프로토콜을 설계하지 않는다.
12. 실제 password, verifier와 token을 Git·artifact·로그에 저장하지 않는다.
13. 설치·제거는 ownership manifest가 소유한 범위만 변경한다.
14. 기존 `ai/prompt-task`는 마이그레이션 검증과 사용자 승인 전에 삭제하지 않는다.
15. 저장소의 민감정보 검사 정책을 모든 commit과 push 경로에 적용한다.

## 구현 순서

### 1단계: Core vertical slice

Domain, Milestone, Objective, Knowledge, Reference와 Task fixture를 검증하고 로컬 SQLite projection을 자동 생성한 뒤 `worklog task list`로 조회한다.

### 2단계: Task 실행 계약

상태 전이, Prompt revision, claim, immutable ControlRequest·Disposition, Run과 operation recovery를 구현한다.

### 3단계: Skill runtime

세 under-claw 스킬 bundle, provider-neutral `RunnerAdapter`, invocation audit와 9.5 review gate를 구현한다.

### 4단계: Flutter GUI

로그인, Domain/Milestone, Task 관리, Prompt, Knowledge, 실행 제어, 동기화와 충돌 화면을 구현한다.

### 5단계: 인증·설치

인증 provider spike와 선정 gate를 통과하고 운영체제별 설치·업데이트·제거 artifact를 만든다.

### 6단계: Agent와 기존 데이터

Hermes 등 headless adapter를 검증하고 기존 일자별 프롬프트를 dry-run 방식으로 마이그레이션한다.

상세 Task와 완료 조건은 [구현 로드맵](08-implementation-roadmap.md)을 따른다.

### 추가요구 구현 상태

- 요구1 실행 Environment 등록·관리: Environment/Agent registry(YAML 정본, 불변 `machine_key` 식별·안전 승격·relink·atomic write)로 구현. 규칙은 [ADR 0002](../adr/0002-environment-registry-and-matching.md)와 [데이터 모델](03-data-model.md)을 따른다.
- 요구2 자료매칭 provenance: `Match`(MAT-) 정본 엔티티와 propose/approve/reject/revoke·immutable 이력으로 구현. Match 화면에서 사용자가 직접 매칭을 생성(`New match`)하고 agent 자동매칭(`Auto-match`)이 근거·신뢰도와 함께 검토 대상으로 제안하므로 "사용자·agent·둘 다" 경로가 앱에서 실제로 도달 가능하다.
- 요구3 다중 agent 통합기억: Domain·Milestone·Task scope와 승인된 Match를 통한 교차-agent Knowledge 회상, supersede/보안필터/출처추적을 Git 정본 기반으로 구현.
- 요구4 Flutter 데스크톱 셸: 공개적으로 관찰 가능한 Orca/Warp 계열의 dense master/detail·navigation·status 패턴을 자체 token으로 구현하고 모든 텍스트를 bundled D2Coding 16pt로 통일했다.
- 요구5 Notion 동시관리: 실제 REST transport, OS secure token, local database mapping, 명시적 `Sync now`, Git commit-before-ack, 충돌 화면을 구현했다. Notion은 정본이 아닌 mirror이며 실제 workspace schema/live credential smoke는 opt-in acceptance로 남는다.

### 운영 경로 구현 상태

- Canonical Git sync: CLI `git-sync`와 Flutter `Sync Git canonical data`가 같은
  Core service를 사용한다. 사전 staged/non-canonical 변경을 거부하고 graph/schema,
  SQLite rebuild와 portable secret scan을 통과한 canonical 변경만 commit한다.
  configured upstream을 fetch/rebase하며 conflict 시 원래 HEAD·canonical bytes·index를
  복구하고 exact lease push만 허용한다.
- Installed runtime: local-only verified descriptor가 JSON protocol, executable와
  independent reviewer checksum/capability를 고정한다. `meta-generate`는 현재 Draft에
  묶인 pending Meta만 만들고, `worker-next-agent`는 승인된 최신 Meta와 별도 reviewer
  verifier가 있는 orchestration descriptor만 실행한다. 실제 Codex/Claude descriptor는
  host acceptance 전 자동 생성하지 않으며 Hermes는 계속 잠겨 있다.
- Unsigned distribution: CI가 GUI·CLI·pinned skills·installer/updater를 하나의
  OS별 archive로 만들고 manifest 전체 hash/size/path/symlink를 설치 전 검증한다.
  update는 complete product payload를 staging하고 app/CLI health 실패 시 이전 설치를
  보존한다. archive checksum은 무결성만 제공하며 publisher authenticity와 플랫폼
  signing은 외부 release gate다.

## 전체 완료 기준

- 개발도구가 없는 macOS, Windows와 Linux 환경에서 설치파일 하나로 실행된다.
- 최초 기기에서 target repository와 repository password를 설정할 수 있다.
- 다른 환경에서 같은 Private repository와 password 정책으로 연결할 수 있다.
- GUI에서 Domain, Milestone, 목표, 사전 지식, 참고자료와 Task를 관리할 수 있다.
- GUI에서 Task 시작·일시중지·재개·중단·완료 요청과 Agent ACK를 확인할 수 있다.
- Agent는 최신 Meta Prompt와 context pack을 사용하고 세 스킬 파이프라인을 통과한다.
- 중복 실행, 요청 경합과 중간 실패 후 복구가 자동 검증된다.
- SQLite를 삭제해도 Git 정본에서 자동 재생성된다.
- 실제 password, token, 고객·사용자 식별정보가 Git과 로그에 남지 않는다.
- 앱만 제거, runtime 제거와 완전 제거가 구분되고 사용자 파일은 보존된다.
- 기존 프롬프트 마이그레이션 결과가 검증되며 원본은 승인 전 삭제되지 않는다.

## Agent 작업 시작 지침

1. 저장소 `AGENTS.md`를 읽는다.
2. 이 문서와 작업 영역의 normative source를 읽는다.
3. `git status --short`로 기존 사용자 변경을 확인하고 보존한다.
4. [구현 로드맵](08-implementation-roadmap.md)에서 선행 조건과 완료 기준을 확인한다.
5. 실제 인증값, 고객정보와 환경파일을 fixture나 문서에 넣지 않는다.
6. 변경 후 schema, test, link, security scan과 해당 플랫폼 검증을 수행한다.
7. 외부 배포·push·대량삭제는 별도 승인 없이 수행하지 않는다.
